# 接口自动化框架规则

> 本文件是接口自动化框架的「约束源」。所有新项目接入、目录创建、用例编写、
> 配置/报告管理，均以本规则为准。通用框架（common 层）已固化为模板，引入新项目
> 时复制模板 → 填 config → 加接口 → 写用例，**不继承任何旧项目业务数据**。

---

## 一、定位与原则

| 原则 | 说明 |
|---|---|
| 工具归工具，项目归项目 | 框架（common 层、分层结构、脚本）与业务数据（config/apis/data/testcases）物理隔离；模板不含真实域名/账号/接口 |
| 即开即用 | 复制模板即可启动新项目，零业务残留 |
| 单一职责 | 接口定义只在 apis、用例只在 testcases、数据只在 data、通用能力只在 common |
| 配置驱动 | 环境/鉴权/服务域名全部走 config，代码不硬编码 |

## 三、接口定义层（apis/）

### 3.1 分模块规则
- 每个业务模块一个子目录：`apis/{模块}/{模块}_api.py`
- 模块按「业务实体」划分，与服务对齐（如 `client`/`house`/`lead`/`deal`/`staff`/`account`）
- 跨服务但同一业务实体，仍归同一模块（如 account 登录在 auth、staff 在 svc-main，分属不同模块）

### 3.2 文件内容约定
每个 `*_api.py` 文件包含三部分：
1. **接口路径常量**（大写 + 下划线）：`SIGN_IN_ENDPOINT = "/auth/account/signInByVerifyCode"`
2. **接口函数**：模块级函数，第一参数为 `api: RequestHandler`，返回 `requests.Response`
3. **内部辅助函数**（如 `_url`）：以 `_` 开头

### 3.3 函数签名约定
```python
def create(api: RequestHandler, *, type: str, name: str, mobile: str, gender: int = 1, **extra):
```
- **keyword-only**（`*` 分隔）：必填参数必须按名传，防止位置错乱
- **`**extra`**：可选字段透传，函数内不写死可选参数列表
- 默认值集中在此，用例调用时不重复写默认参数

### 3.4 URL 组装
- 同服务接口：用 `_url(api, "/path")` 拼接 `config.service_url(服务名) + 前缀 + path`
- 跨域接口（登录走 base_url）：直接传相对路径给 `api.post(path)`，由 request_handler 自动拼 base_url
- **函数返回原始 Response**，提取/断言交给用例，不在 apis 层做断言

### 3.5 禁止事项
- ❌ 用例里拼 URL（`f"{svc-main}/api/client/create"`）
- ❌ 用例里组装 payload dict（除非场景链动态值）
- ❌ apis 层做业务断言（只发请求，不判断对错）

## 四、测试用例层（testcases/）

### 4.1 分模块规则
- 与 apis 模块一一对应：`testcases/{模块}/test_{模块}.py`
- 单接口测试：`testcases/{模块}/test_{接口名}.py`
- 场景链测试：`testcases/{模块}/test_{模块}_scenario.py`

### 4.2 用例铁律
> **用例只调用 apis 函数，不拼 URL、不存放参数。**

- 参数来自 data 层（YAML）或场景链动态生成（如随机手机号）
- URL 完全由 apis 层管理

### 4.3 数据驱动用例
- 请求体/期望值存 `data/{模块}/{接口}.yaml`
- 用例用 `@pytest.mark.parametrize` 从 YAML 加载
- **endpoint 不写进 YAML**，从 apis 路径常量取（数据只管数据，接口归接口）

### 4.4 场景链用例
- 使用 `common.extractor.Context` 在步骤间传递动态值（如创建后返回的编码 → 后续查询）
- 支持 `${var}` 占位符替换

### 4.5 Allure 元信息
每个用例标注：
- `feature`（业务模块）/ `story`（场景分类）/ `title`（编号+名称）
- `severity`（blocker/critical/normal/minor/trivial）
- `description` = 排查理由（让报告一眼看懂"这用例在查什么"）
- 自动 `epic=接口自动化`（conftest autouse，与 UI 报告区分）

### 4.6 标记（markers）
`smoke` / `login` / `auth` / `regression` / `security`（在 pyproject 声明，用例按需打标）

## 五、数据层（data/）

- 按模块分子目录：`data/{模块}/{接口}.yaml`
- 存放内容：请求体、期望值、排查理由（reason）、风险提示（note）、severity
- **不存放**：endpoint（归 apis）、鉴权信息（归 config）
- 动态参数（随机手机号等）在用例里生成，不写死在数据文件

## 六、通用工具层（common/）

> 原则上不改动，原样从模板复用。能力清单：

| 文件 | 能力 | 用法 |
|---|---|---|
| `config.py` | 多环境加载、`service_url(name)`、env 覆盖 base_url | `Config.load(env)` / `cfg.service_url("svc-main")` |
| `request_handler.py` | Session 封装、自动拼 base_url、超时/重试、default_params 合并 | `api.post(path, json=...)` |
| `auth.py` | 登录取 token、注入头/查询参数、业务多头+岗位鉴权 | fixture 内调用，用例不直接用 |
| `assert_util.py` | 状态码/jsonpath相等/存在非空/包含/jsonschema | `assert_jsonpath(resp, "$.code", 0)` |
| `extractor.py` | jsonpath/正则提取、Context 上下文 | `extract_by_jsonpath(resp, "$.result")` |
| `throttle.py` | 按 key 节流（防频控） | `login_throttle.wait(mobile)` |

## 七、鉴权链路模式

### 7.1 三句柄 fixture（conftest.py）
| fixture | 鉴权 | 用途 |
|---|---|---|
| `api` | 无鉴权 | 测试鉴权失败、无权限场景 |
| `auth_api` | 单 token（Authorization 头 + accessToken 查询参数） | 普通需登录接口 |
| `biz_api` | 业务多头 + 岗位头 | 业务接口（多服务权限校验） |

### 7.2 鉴权全由 config 驱动
`config.yaml` 的 `auth` 段定义：登录端点、token 提取路径、头/查询参数、业务多头、岗位信息接口。common/auth 按配置执行，**不硬编码任何鉴权细节**。

> 新项目鉴权方式不同时，改 config.yaml 的 auth 段即可，不改 common/auth 代码。

## 八、多环境配置约定

### 8.1 config.yaml 结构
- `defaults`：全局默认（timeout/retry）
- `environments`：每环境 base_url + services（业务服务域名）
- `auth`：登录/鉴权链路配置

### 8.2 敏感值约定
- 真实账号/密钥/token 放 `.env`（已被 .gitignore 忽略）
- 代码通过 `os.environ` 读取，config.yaml 只放结构不放明文密钥
- base_url 可被 `.env` 的 `<ENV>_BASE_URL` 覆盖

### 8.3 禁止事项
- ❌ config.yaml 硬编码真实密钥
- ❌ 用例/apis 里写域名
- ❌ 用例里写账号密码

## 九、报告归档规则

### 9.1 目录结构
```
reports/
├── allure-results/          # 原始结果（运行产物，gitignore）
├── allure-report/           # 最新报告（gitignore）
└── 08月/                    # 按月
    └── 0807/                # 按日（月日，前导零，排序友好）
        └── 001/             # 当日序号递增（3位补零）
            ├── index.html   # Allure 报告
            └── run_info.txt # 运行时间/退出码/allure版本
```

### 9.2 命名规则
- 月份：`08月`（前导零 + 中文"月"，排序友好且可读）
- 日期：`0807`（MMdd）
- 序号：`001` 起，当日每次运行取「已有最大序号+1」，3位补零
- run_info.txt 记录完整 yyyy-MM-dd HH:mm:ss 时间戳便于追溯

### 9.3 保留策略
- 归档**永久留存**，手动删除才消失
- 最新报告始终在 `reports/allure-report/`（每次运行覆盖）

### 9.4 查看方式
（file:// 协议会致 Allure "500 Failed to fetch"，改用本地 HTTP 服务）
```powershell
python -m http.server 8089 --directory reports\allure-report
# 然后打开 reports\open_report.html（重定向页）
```

## 十一、新项目接入流程

1. **复制模板**：`api-automation-template` → 改名为新项目（如 `xxx-api-test`）
2. **填 config/config.yaml**：base_url、services、auth（登录端点/账号/鉴权链路）
3. **建 .env**：复制 `.env.example` → `.env`，填敏感值（如有）
4. **建接口定义**：`apis/{模块}/{模块}_api.py`，从后端/前端代码提取接口，写路径常量+函数
5. **建数据**：`data/{模块}/{接口}.yaml`（数据驱动用例）或场景链直接在用例生成
6. **写用例**：`testcases/{模块}/test_*.py`，只调用 apis 函数 + 断言
7. **运行**：`.\run_all.ps1`，报告按日期归档
8. 删除 `example/` 示例（或改造为首业务模块）

## 十二、pytest 配置约定

`pyproject.toml` 固化以下配置（模板内置，新项目不改）：
- `testpaths = ["testcases"]`
- `pythonpath = ["."]`：保证 apis/common 可导入
- `addopts` 含 `--import-mode=importlib`：支持模块化目录下同名 test 文件
- `--alluredir` + `--clean-alluredir`：每次运行清空旧结果
- markers 声明
