# 需求评审能力验收清单

用于验证“需求评审”智能体及 `requirement-testability` 共享能力是否真正执行基于事实证据的多轮闭环。该清单只评估能力，不保存任何项目业务资产。

## 一票否决项

出现任意一项，本次能力验收不通过：

- 无证据的内容被写成需求事实或验收条件。
- 模糊、缺失或冲突的内容被智能体自行补全。
- 产品答复只保留总结，没有保存未经改写的原文。
- 问题从“待确认”直接变为“已关闭”。
- 收到答复后未创建新评审轮次。
- 新轮次改写或删除了评审文件中的既有轮次记录。
- 复评使用已有编号承载了不同语义的新事实、验收条件、问题或风险。
- 一份确认覆盖多个问题时未逐项判断，或材料内部存在冲突却关闭了相关问题。
- 存在未关闭的 `P0` 问题时，评审结论却标记为通过。

## 场景一：明确需求事实

### 输入

需求明确描述角色、操作和可观察结果。

### 预期

- 登记原始需求证据 `E-NNN` 及具体位置。
- 提取 `F-NNN`，不扩大原文含义。
- 验收条件同时引用事实和证据。
- 创建一个评审文件，包含当前有效结论和 `REV-001` 摘要。

## 场景二：需求存在歧义

### 输入

需求使用“适当、常见、尽快、支持大文件”等无法直接判定的描述。

### 预期

- 不生成虚假的精确边界。
- 分别登记 `Q-NNN`，包含依据、影响、确认对象、优先级和“待确认”状态。
- `P0` 问题存在时，下一步为“等待产品确认”，评审结论为阻塞。

## 场景三：收到产品答复

### 输入

产品经理针对一个问题提供带身份和时间的书面答复。

### 预期

- 原文保存到 `01-source/confirmations/confirmation-C-NNN.md`。
- 登记确认记录和新证据，关联原问题。
- 充分答复将问题更新为“已答复待复评”，不直接关闭。
- 不在确认登记阶段直接修改验收条件。

## 场景四：根据答复复评

### 输入

存在“已答复待复评”的问题和对应确认记录。

### 预期

- 在同一评审文件中追加下一编号的 `REV-NNN` 增量，既有轮次记录保持不变。
- 重新检查事实、验收条件、范围、风险、假设和其他问题。
- 使用 `CHG-NNN` 记录所有受影响内容及依据。
- 答复充分且同步完整后，原问题才更新为“已关闭”。
- 答复产生新歧义时，创建新问题并继续确认循环。

## 结构完整性

- [ ] 当前汇总注明对应的最新评审轮次
- [ ] 当前评审有评审时间和执行人或智能体
- [ ] 每轮都有输入证据、结论和下一步动作
- [ ] 每条事实都能定位到有效证据原文
- [ ] 每条验收条件都关联事实和证据
- [ ] 每个问题都有合法状态和确认对象
- [ ] 每条确认都关联问题和原文证据
- [ ] 每项跨轮变化都有变更编号
- [ ] 复评前已建立已有编号语义清单，新增语义未复用旧编号
- [ ] 多问题确认已逐项判断充分性，冲突项保持“需继续确认”
- [ ] 评审结论与 P0 问题状态一致（存在未关闭 P0 时不得标记为通过）
- [ ] 没有内容的确认、风险、假设和变更区块已省略

## 通过标准

四个场景全部满足预期、结构完整性全部勾选，且不存在一票否决项，能力验收才通过。
